# P2: мобильная проверка критичных страниц — результат

Ссылка на карточку: `docs/plans/product/20260912-seo-improvement.md`, приоритет P2.
Проверяемые страницы (дословно из раздела «Google, 24 июля — 9 сентября 2026»):
`/`, `/how-to-play`, `/commands`, `/coach`, `/blindfold`.

## Метод измерения

`scripts/mobile_audit.py` — говорит с уже установленным на машине Chrome
(`google-chrome`) напрямую по Chrome DevTools Protocol (свой минимальный
клиент поверх RFC 6455, без новых зависимостей): headless-профиль на время
прогона, мобильный viewport 390×844 (`deviceScaleFactor: 3, mobile: true`),
мобильный user-agent, кэш браузера отключён. По каждой странице:

- перед сохранением среза проверяется, что финальный ответ на переход —
  `HTTP 200` и что его конечный URL (после возможных редиректов) совпадает
  с запрошенным маршрутом; иначе снятие среза для этой страницы падает
  с ошибкой вместо того, чтобы молча сохранить срез 404/500 или чужой
  страницы после редиректа;
- после события `load` (+0.5 c на отложенные layout-shift) скрипт читает
  `performance` в самой странице:
  - `domContentLoadedEventEnd` / `loadEventEnd` — время до DOMContentLoaded
    и load;
  - `navigation.transferSize` + `Σ resource.transferSize` — объём передачи;
  - накопленный `layout-shift` без `hadRecentInput` (CLS) через
    `PerformanceObserver({buffered: true})`, подключённый до первой
    отрисовки;
  - `document.documentElement.scrollWidth` против `window.innerWidth` —
    горизонтальный оверфлоу;
  - положение обязательной команды запуска («...запусти навык Шахматы
    с Юрой...», поиск без учёта регистра по тексту DOM) через
    `getBoundingClientRect()` — команда считается видимой в первом экране,
    если у неё ненулевые `width`/`height` и `0 <= top < window.innerHeight`.
- весь прогон (все пять страниц) пишется во временный каталог и публикуется
  под `docs/qa/mobile-audits/<дата>-<label>/` одним атомарным переименованием
  только после успеха всех пяти страниц; при ошибке временный каталог
  удаляется, а целевой каталог с датой-меткой не появляется вовсе. Повторный
  запуск с уже занятым именем каталога (`<дата>-<label>`) завершается
  ошибкой и ничего не перезаписывает.

PageSpeed Insights и Lighthouse не использованы: анонимная квота PageSpeed API
в песочнице отвечает `429 RESOURCE_EXHAUSTED` без ключа, а оценка стороннего
продукта не входит в задачу карточки. Список страниц берётся из констант
`yura_chess.presentation.website`, а не захардкожен — как и в
`scripts/submit_indexnow.py`, страница не может незаметно выпасть из аудита.

### Стенд

Один и тот же стенд для обоих срезов:

- реальное FastAPI-приложение (`yura_chess.main:create_app`) поверх уже
  работающей в этом окружении dev-MariaDB (`127.0.0.1:3307`, та же база и
  те же данные для обоих запусков — единственная переменная между срезами
  это код `src/yura_chess/presentation/website.py`) и реального Stockfish
  (`/usr/games/stockfish`);
- между 501c1ac и HEAD не менялись ни миграции, ни `src/yura_chess/storage/**`
  (`git diff --stat 501c1ac HEAD -- migrations/ src/yura_chess/storage/`
  пустой), поэтому переиспользование одной базы для обоих срезов не искажает
  сравнение;
- «до» снято на файле `src/yura_chess/presentation/website.py` версии
  `501c1ac` (временно подставлен через `git checkout 501c1ac --`, затем
  восстановлен обратно на HEAD; вне этого файла `git diff --stat 501c1ac HEAD`
  касается только `scripts/mobile_audit.py`, `docs/qa/*`, `tests/test_health.py`
  — рантайма это не касается), сервер поднят на `127.0.0.1:8010`;
- «после» — HEAD этой ветки (обе ветки-предшественницы карточек 0 и 1 уже
  влиты), сервер поднят на `127.0.0.1:8011`.

Команды запуска (идентичны для обоих срезов, отличается только выставленная
версия `website.py` и порт):

```bash
uv run uvicorn yura_chess.main:create_app --factory --host 127.0.0.1 --port 8010
uv run python scripts/mobile_audit.py --label pre-release --base-url http://127.0.0.1:8010
# ... восстановить website.py на HEAD, поднять на 8011 ...
uv run python scripts/mobile_audit.py --label post-release --base-url http://127.0.0.1:8011
```

Сырые отчёты: `docs/qa/mobile-audits/2026-09-13-pre-release/`,
`docs/qa/mobile-audits/2026-09-13-post-release/`. У каждой страницы в JSON
также записаны `httpStatus` (везде `200`) и `finalUrl` (везде совпадает
с запрошенным путём — ни одна страница не отдала ошибку и не увела на
другой маршрут).

`/commands`, `/coach` и `/blindfold` на 501c1ac не показывали обязательную
команду запуска нигде на странице вообще (`launchCommandVisible: false`,
`launchCommandTop: null` — на этих трёх страницах текста «запусти навык
Шахматы с Юрой» не было ни в первом экране, ни ниже). На HEAD в `header`
всех трёх страниц добавлен блок `.launch`/`.launch-command`
(`src/yura_chess/presentation/website.py`, headers `COMMANDS_PAGE_HTML`,
`COACH_PAGE_HTML`, `BLINDFOLD_PAGE_HTML`) — тот же CSS-класс, что уже
использовался на главной, без новых стилей. CDP-измерение подтверждает:
после правки у всех пяти страниц `launchCommandVisible: true`.

Прирост объёма передачи на `/how-to-play`, `/coach`, `/blindfold` (+5.4–5.7%)
в основном соответствует добавленному в HEAD тексту (примеры голосовых
циклов, готовое упражнение — см. `git diff 501c1ac HEAD --
src/yura_chess/presentation/website.py`); на `/commands`, `/coach` и
`/blindfold` небольшую часть прироста (около 250–300 B) даёт добавленный
блок с командой запуска. `load` не вырос заметно ни на одной странице,
CLS остался нулевым, оверфлоу не появился. Разброс DOMContentLoaded/load в
единицы миллисекунд между срезами — шум локального сервера без сетевой
задержки, не сигнал деградации.

**Правки производительности не вносились** — ни один из пяти срезов не
показал измеримого узкого места (роста `load`, ненулевого CLS или оверфлоу),
а карточка прямо запрещает спекулятивную оптимизацию без такого измерения.
Добавление команды запуска в `/commands`, `/coach` и `/blindfold` —
не оптимизация производительности, а исправление содержимого: страница
не показывала обязательную информацию (критерий приёмки), CDP-измерение
это подтвердило и теперь проверяет на каждом прогоне.

## Структурная проверка (HEAD)

- **Команда запуска и польза в первом экране** — подтверждено CDP-измерением
  выше (`launchCommandVisible: true` на всех пяти страницах), а не только
  чтением исходника.
- **Навигация читаема** — `.site-nav` на `max-width: 760px` (строки 411–421)
  разворачивается в полноширинный флекс-ряд, `min-height: 40px` на пункт.
- **Горизонтального скролла нет** — `main` ограничен `min(1080px, calc(100% - 32px))`
  (строка 105, `calc(100% - 20px)` на `max-width: 520px`, строка 438); измерение
  CDP подтверждает `documentWidth == viewportWidth` на всех пяти страницах
  и в «до», и в «после».
- **`prefers-reduced-motion` поддержан** — `@media (prefers-reduced-motion: reduce)`
  (строки 384–400) отключает transition/animation; блок не затронут диффом
  501c1ac → HEAD.

## Зависимость от карточки послерелизных сигналов

Дорелизный срез (`pre-release`, на 501c1ac) снят и сохранён до публикации
карточек 0/1 в этой цепочке веток; послерелизный срез (`post-release`, на
HEAD) — после. Карточка послерелизных сигналов может опираться на оба файла
как на зафиксированный «до/после».
